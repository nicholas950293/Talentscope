# Talentscope 工作說明書（SOW）

> 適用於職訓團體專案。未有真實分工、工期或日期的項目一律標示「待團隊確認」、「建議值」或「尚未排定」。

## 1. 專案背景

團隊以技術面試流程分散、角色交接不透明及 AI 決策責任不清為問題，建立 Talentscope 三角色互動 MVP，展示 HR、技術主管與面試者從邀請到人類決策的完整產品概念。

## 2. 專案目標

- 提供可展示的三角色面試協作流程。
- 建立一致的題庫、組卷、作答、提示、審核與結果介面。
- 清楚呈現 AI 只提供提示、初評與證據，人類保留最終決策權。
- 建立能支援團隊協作與後續開發的文件基線。

## 3. 工作範圍

### 目前 MVP 工作

- 三角色 Demo 入口與角色專屬導覽。
- HR Dashboard、候選人、摘要與結果介面。
- 技術主管題庫、組卷、邀請與審核介面。
- 面試者驗證、說明、作答、提示與提交流程。
- 統一九種面試狀態與 RWD 視覺。
- SSR smoke test、typecheck 與 vinext build。

### Sprint 2 文件工作

- 專案總覽、SRS、PDD、架構、資料模型、使用流程、測試計畫與 SOW。
- README 更新與文件索引。
- 角色、狀態、Mock 邊界與規格標記一致性檢查。

## 8. 驗收標準

- 交付內容符合 [SRS](./SRS.md) 的狀態標記，不把 Mock 描述成正式能力。
- 三角色入口與權限視角明確不同。
- 九種面試狀態名稱跨 UI 與文件一致。
- AI 可依候選人要求協助解題，但不自動評分或決定錄取／淘汰；候選人對最終答案負責。

## Sprint 6A 交付

新增 server-only Gemini endpoint、Mock／Gemini adapters、versioned prompt、輸入與上下文限制、統一錯誤契約及自動測試。正式金鑰設定、真實配額驗證、持久化、Audit Log、跨角色同步與 AI 協作評分不包含在本輪。
- README 的安裝、啟動、測試與 build 指令和 `package.json` 一致。
- 文件路徑、表格、Mermaid 與交叉連結可讀。
- 未執行的測試不標記 Passed。

## 9. 風險與因應方式

| 風險 | 影響 | 因應 |
|---|---|---|
| Demo 被誤認為正式系統 | 錯誤期待與安全風險 | UI 與文件標示 Mock／Planned |
| 規格與程式碼漂移 | 開發與驗收爭議 | 每 Sprint 更新狀態表與交叉連結 |
| 單一大型元件 | 維護與測試成本升高 | 後續依角色、domain 與 service 漸進拆分 |
| AI 偏誤或洩漏答案 | 公平性與評估效度下降 | 分級提示、人工覆核、模型／prompt 版本與紅隊測試 |
| 個資與就業決策資料外洩 | 高風險 | 最小化、RBAC、加密、保存政策與 Audit Log |
| 候選人網路中斷 | 答案遺失 | durable autosave、斷線提示與恢復測試 |
| 工期或分工未確認 | 範圍失控 | 里程碑前完成估時與 owner 指派 |

## 10. 需求變更管理

1. 以 Issue／變更單記錄目的、影響、優先級與驗收標準。
2. Product Owner 與受影響角色共同確認；負責人待團隊指派。
3. 變更 SRS 的需求狀態與對應 PDD、資料模型、測試案例。
4. 涉及狀態、AI 決策、個資或權限者須額外做風險審查。
5. 未經確認的未來構想維持 Planned，不納入當期完成承諾。

## 11. 預估後續 Sprint

建議值：每個 Sprint 先完成一條可驗證的垂直切片，不同時展開全部外部整合。優先順序為資料持久化與權限 → 真實面試 token／提交 → Email／AI → 品質與部署。實際 Sprint 長度、容量及截止日待團隊確認。

## 12. 專案完成條件

MVP 原型專案可視為完成的條件：

- 已同意的 Sprint 範圍與驗收案例完成。
- 重要缺陷有修復或接受紀錄。
- typecheck、test、build 通過，未執行項目有明確說明。
- 文件與程式碼版本一致，Mock／Planned 邊界清楚。
- Demo 操作方式、限制與下一步可由團隊成員說明。

正式產品完成條件必須另行定義安全、隱私、SLA、法遵、監控與使用者試點標準；目前尚未排定。
